1. Overview, supported models and safety

ComCon opens a radio's physical serial port and can provide either a RAW byte bridge to a paired virtual COM port or a command-capable local named-pipe IPC session. Profiles have independent configuration and lifecycle; the current configuration model provides up to four profile slots. ComCon is not a generic TCP/HTTP API, a radio safety interlock, or a substitute for the client application that creates and interprets radio commands.

Platform: Windows 11 x64. The planned distribution is a self-contained portable ZIP, so no separate .NET installation is needed to run that package. Use the release notes if a particular prerelease lists a narrower scope.

Radio scope: the intended initial models are Icom IC-7400, Icom IC-7600 and Kenwood TS-590SG, using CI-V or Kenwood ASCII as applicable. Implementation and test evidence do not certify every model, firmware or command. Yaesu ASCII/RAW support is experimental and hardware-unverified; Yaesu command IPC is unavailable. Treat each profile/model as unverified until its release notes and your own approved checks say otherwise.

Safety: ComCon has no safety certification and is not a safety filter. RAW forwards bytes unchanged, including transmit and tune commands. Command IPC also carries client-originated bytes; successful delivery or a cached value does not prove that the radio received, understood or safely completed an operation. You remain responsible for transmitter operation, correct radio/port selection, and preventing unintended transmission.

Do not let another application open the same physical radio port directly while ComCon owns it. Stop any bridge before changing cabling or making a connection handover.

Help, About and first use

The main window has Help (F1) and About buttons at the top right. Help (F1) and the F1 key open this local Help\index.html in the default browser. If the page or browser launch is unavailable, the app reports an error; there is no silent online fallback. About shows version, attribution, license/notices, repository/support links and may offer optional Ko-fi support. It says ComCon is free and gives no safety certification.

On first use for a Windows user, a welcome offers Continue, Open Help and an optional Support on Ko-fi (optional) button. Continue or closing the window dismisses it without donating; it is not repeated on ordinary launches or updates. If the dismissal cannot be saved, ComCon shows a warning and the welcome appears again next start. Its per-user marker is %LOCALAPPDATA%\ComCon\FirstUse.json; delete that file to see the welcome again. Help and welcome do not start/stop a bridge or open a radio connection. External links are followed only on explicit action.

2. Prerequisites

  • Windows 11 x64 and the ComCon portable ZIP from official GitHub Releases.
  • The included self-contained runtime; no separate .NET installation is needed for that package. A framework-dependent developer build has different prerequisites and may require the matching .NET 10 Windows Desktop Runtime; follow the developer instructions for source builds.
  • The correct Windows serial driver for your radio interface, installed from a source you trust. ComCon does not install it.
  • A virtual COM pair only for a legacy COM application (for example Commander) connected through RAW. Command-IPC-only use needs no virtual pair.
  • The radio-control client software you plan to use, installed and configured separately.

com0com: this is an optional third-party virtual null-modem driver referenced as one way to provide paired virtual COM ports. It is not bundled, installed or configured by ComCon. Check current Windows 11 compatibility, signatures, licensing and official instructions before use. This guide does not ask you to disable Windows signing, Defender, SmartScreen or other security protections. Do not install a virtual-pair driver if your setup does not need one.

3. Download, verify and install

  1. Open the BattleHook/ComCon Releases page and choose the Windows 11 x64 portable ZIP for the intended release. Read its release notes. If no asset and checksum are available, wait for the release; do not treat a source checkout as a published package.
  2. Download the ZIP and its published SHA-256 checksum. In PowerShell, replace the sample name with the downloaded file: 
    Get-FileHash .\ComCon-Windows-x64.zip -Algorithm SHA256
    Compare the full result with the checksum for that exact asset. Do not extract or run a file whose hash differs.
  3. Extract the ZIP to a folder your Windows user can write to, such as under %LOCALAPPDATA% or your user Documents folder. Keep the package layout together. Do not extract over an existing installation before backing it up.
  4. The initial package is unsigned, so Windows may show a SmartScreen trust prompt. After verifying the source and checksum, select More info → Run anyway only for the ComCon file you intentionally downloaded. If the prompt differs or your policy blocks it, stop and ask your administrator; never disable security protection.
  5. Start ComCon.UI.exe. No bridge starts merely because the app opened. Check the displayed version; use Help or F1 to open this guide.

Expected release contents include ComCon.UI.exe, Help\index.html, LICENSE.txt, THIRD-PARTY-NOTICES.md and a licenses\ folder. A missing expected file is a packaging issue; contact support instead of downloading a replacement from an unknown source.

This guide is inside the package's Help folder. The links point to the files beside the executable: MIT license text (../LICENSE.txt) and third-party notices (../THIRD-PARTY-NOTICES.md). In the development source tree, these documents are at the repository root.

4. Ports and connection layouts

Legacy application using RAW

Radio serial port  <──>  ComCon physical-port endpoint
                                      │
                              ComCon virtual endpoint
                                      │
                            virtual COM pair / driver
                                      │
Legacy client (e.g. Commander)  <──>  paired peer COM port

COM names are conceptual. Select the radio port and ComCon-side virtual endpoint in the profile; the legacy client opens the paired peer. ComCon owns the physical radio port. A virtual pair is supplied and maintained separately.

Command-capable IPC client

Third-party client  <── local Windows named pipes ──>  ComCon profile
                           CAT byte stream + control/notifications
ComCon profile  <── serial connection ──>  Radio

The client identifies a rig profile by a mapped UUID. IPC does not use TCP, expose a generic JSON CAT-command API or require a virtual COM pair unless a separate legacy app also needs one. See Connect your own IPC client.

5. Configure profiles

ComCon starts with profile slots that can be named and configured. A profile contains enabled state, physical and optional virtual/Commander ports, adapter/framing, serial settings and optional command-IPC settings. Configuration files are validated JSON. Prefer the UI, back up before hand-editing, and use Validate after loading or changing a file.

  1. Select a profile and give it a label that identifies the radio/connection.
  2. Set Enabled only after checking radio and ports. Select the correct model/adapter and protocol framing. CI-V, Kenwood ASCII, Yaesu ASCII and None are distinct choices; don't select a mode just because a device uses similar commands.
  3. Set baud rate, data bits, parity, stop bits, handshake, DTR and RTS to match the radio/interface and client. Defaults are not evidence of your radio's settings. Avoid changing several values at once.
  4. For RAW, set the physical and ComCon-side virtual COM ports. In the legacy app, choose the paired peer. Confirm the actual pair mapping rather than guessing port numbers.
  5. For command IPC, enable that profile's command-IPC option and import/map the client's rig-profile UUID. The identity is not the display/model name or radio address; the target ComCon profile supplies physical-port and serial configuration.
  6. Choose Validate; correct every error. Use Save configuration... to save to a user-writable location and Load configuration... to reopen a saved file. Saving alone does not start a bridge.

Configuration JSON is schema-versioned and uses exact lower-camel-case names. The UI remembers the last configuration path with local preferences. If the file moves, load it explicitly. Do not reuse another station's settings without checking every port, address and identity.

Autoconnect label: the saved flag is not automatic startup restoration. Selecting a stopped saved IPC Autoconnect profile can offer a start-list workflow; review and confirm the list. Loading/saving or launching ComCon does not silently start profiles.

6. RAW and command IPC

Choose the transport your client requires
ModeConnectionBoundary
RAWByte forwarding between the radio endpoint and ComCon's virtual-COM endpoint.Bytes are unchanged; RAW is not a safety filter and may carry transmit/tune commands.
Command IPCA named-pipe CAT byte stream plus a separate profile-scoped control/notification pipe.The client supplies bytes and interprets replies. Delivery outcomes are not radio-operation confirmations.

The modes have different setup, port and client requirements. Select the mode your application supports. Do not let another application open the ComCon-owned physical port. A successful pipe connection or physical write does not prove a command completed.

7. Start and stop bridges

  1. Load/configure a profile, validate and save it.
  2. Refresh ports and verify the physical/virtual endpoint names against Windows and your cabling/pair documentation.
  3. Select a profile and choose Start selected, or choose Start list... to review a set. Confirm only after verifying every selected radio and port.
  4. Check the profile overview for actual state, saved mode, mapping and any conflict/fault. A start request is not proof that a bridge is running.
  5. Use Stop selected for one profile or Stop all... for active profiles. Confirm the target and wait for final status before changing a port or cable.

Profiles can run independently only when their physical and virtual port assignments do not conflict. Treat a conflict as a reason to correct configuration, not force a second owner. A faulted/retained profile may reserve ports until it stops or is explicitly recovered. ComCon does not restore radio sessions at app startup. Do not close the app as a substitute for deliberate stop while a profile is active.

8. Commander, HSC and other clients

Commander / legacy COM client

Use RAW when a legacy application expects a COM port. A separate virtual pair is required: ComCon opens one endpoint and the legacy app opens its peer. Configure the client for the matching model, address and serial/protocol behavior. Exact settings depend on your radio and application.

Ham Shack Console (HSC)

HSC is not a ComCon runtime dependency. A particular HSC setup may separately need an HSC client component and compatible version/configuration. Follow HSC's own release instructions; ComCon does not install HSC. HSC is one possible IPC client, not a prerequisite for the developer workflow below.

Connect your own IPC client

This describes command IPC. Use a release whose notes explicitly enable it. For first connection, use a configured profile and synthetic/offline setup where available; do not start a real radio merely to test a pipe handshake. This is local Windows named-pipe IPC, not TCP/network access.

Prerequisites and target mapping

  • Use a client rig-profile UUID mapped by ComCon to exactly one profile ID 1–4. It is a persistent canonical lowercase hyphenated UUID, not model name or CI-V address.
  • The ComCon profile must be enabled, configured for command IPC, and explicitly started. Check status for profile/IPC readiness.
  • Only one IPC session may own a profile at once. Separate profiles may have separate sessions, up to four profile slots. Commander COM may coexist on a profile when supported, but two IPC owners may not.

The UUID mapping is configured on the ComCon side; present the client's UUID and use the returned ComCon profile/session identity. The client's local rig-profile file need not be present at runtime. Do not rely on somebody else's station settings.

Production pipe roles and setup order

  1. Connect to shared CAT pipe ComConCmd_Cat. Send framed JSON cat.handshake with contractVersion = comcon-ipc-v1 and rigProfileId.
  2. Read the framed response. On cat.accepted, retain integer profileId and UUID sessionId. On cat.rejected, inspect errorCode/reason and stop setup.
  3. Connect to ComConCmd_Cat_Control_Profile{profileId}, replacing the placeholder with accepted profile number. Send control.bind with that same profile/session identity; require control.bound, else handle control.rejected.
  4. Send framed cat.ready with the same identity over CAT. Only after validation may CAT carry raw bytes. Never send CAT bytes before this boundary. There is no success reply/ACK for cat.ready.
  5. Keep both pipes open. Close cleanly on shutdown. Lost/invalid control channel ends the session; establish a fresh session rather than assuming reconnect/replay.

Framing and exact envelope contract

Each setup/control JSON object uses strict UTF-8, preceded by a four-byte unsigned big-endian payload length; the prefix is not included. Payloads are limited to 16,384 bytes. No newline, comments, trailing commas or unknown fields. Names are case-sensitive. This is not the separate read-only JSON-lines status pipe. After readiness, CAT is a raw byte stream, not JSON or length-prefixed CAT records.

Every envelope has messageType and contractVersion. Session-associated envelopes also have profileId and sessionId. UUIDs are canonical lowercase hyphenated strings. notificationSequence and recordSequence are positive decimal strings, not JSON numbers.

Message types and additional fields
MessageDirectionAdditional fields
cat.handshakeclient → ComConrigProfileId
cat.accepted, control.boundComCon → clientprofileId, sessionId
cat.rejectedComCon → clienterrorCode, reason
control.bind, cat.readyclient → ComConprofileId, sessionId
control.rejectedComCon → clienterrorCode, reason; identity only if validated
record.rejectedComCon → clientnotificationSequence, recordSequence, deliveryStatus=NOT_SENT, reason
record.outcomeComCon → clientnotificationSequence, recordSequence, deliveryStatus; reason only for non-success
framing.notificationComCon → clientnotificationSequence, errorCode, reason
session.notificationComCon → clientnotificationSequence, event=session.ended, reason
notification.ackclient → ComConnotificationSequence

Every structured record, framing or session notification requires an ACK carrying its exact notificationSequence. Process a repeated notification once per session/sequence, but ACK it again. ACK confirms notification receipt only; it never authorizes CAT write retry.

The implementation bounds setup to 5 seconds, pending notifications to 32 (and 32 KiB), deferred acknowledgments to 8, and ACK wait to 2 seconds with a 500 ms retry interval. Retransmission is of the identical notification envelope/sequence only. If an ACK deadline expires, or the control channel fails, the session ends. Never replay a CAT record whose delivery is uncertain.

Delivery outcomes, errors and cleanup

  • WRITE_SUCCEEDED means ComCon's physical write completed; it does not mean the radio received, processed or acknowledged the command.
  • NOT_SENT means implementation proved the record was not written. UNKNOWN_DELIVERY means dispatch/write status is uncertain. Never automatically repeat either record.
  • Setup rejections use stable uppercase error codes such as RIG_PROFILE_NOT_MAPPED, PROFILE_BUSY, UNSUPPORTED_VERSION, CONTROL_BIND_TIMEOUT or CAT_READY_TIMEOUT; inspect both code and human-readable reason.
  • Framing alerts use FRAMING_ANOMALY or FRAMING_OVERFLOW. The only defined lifecycle event is session.ended. A fatal control-protocol error may close the session without a final lifecycle notice.

Close both pipe streams on cancellation or setup/read/write error. A new session gets a fresh UUID and sequence spaces starting at 1. Do not claim transparent reconnect, radio resynchronization or command completion.

Minimal C# connection example

Open the standalone C# example (no third-party packages). In a .NET 10 console project, use it as Program.cs and run dotnet run -- <mapped-lowercase-rig-profile-uuid>. It performs the two-pipe handshake, sends cat.ready, prints control notifications and acknowledges them. It deliberately sends no CAT bytes, so it does not query, transmit or tune the radio. Build and validate an adapted client against the release; this guide task did not run a build or connect to live hardware.

9. Status, recovery and appearance

The status area and profile overview report saved mode and actual state, selected endpoint mappings, IPC pipe/session information when applicable, legacy connection state and visible fault reason. Follow current status rather than assuming a previous start remains active.

  • Recover Legacy appears for eligible legacy-client recovery states. Use it after addressing the displayed cause; it is not a radio reset or a guarantee of resynchronization.
  • Recover IPC... is an explicit service-recovery action when enabled. Review affected profiles and status; it does not restore a client session or safely repeat a command.
  • UI Styling... opens appearance settings. Theme/color preferences are per-user, not radio profile configuration. UI colors are stored in %LOCALAPPDATA%\ComCon\UiColors.json.
  • Capture raw CAT traffic controls sensitive diagnostics; see Logs and diagnostics. Capture is not a safety measure or command confirmation.

10. Safe checks and live-radio boundaries

Before connecting hardware

  • Validate with no bridge running. Confirm model, physical port, serial settings, virtual pair and client endpoint.
  • Use hardware-free or synthetic endpoints for developer handshake/framing checks. An IPC handshake is not a radio check.
  • Read release notes and radio/client manuals. Arrange an operator-approved test plan and prevent unintended transmission.

When an operator approves a radio check

Begin only with the radio in an appropriate state and a known read-only query supported by the exact radio/client combination. Monitor radio display and ComCon status. Do not use transmit, tune, keying or power-control commands as tests. Stop if identity/state/response is unexpected. A reply, pipe connection or successful write proves neither safety nor operation completion.

11. Troubleshooting

Port is missing
Choose Refresh ports; check Device Manager, cable/interface power and vendor driver. Verify the selected COM name; do not guess.
Port is busy or profiles conflict
Stop its owning profile and close applications that opened the radio/virtual port directly. Check reservations and correct duplicate physical/virtual mappings.
Virtual pair does not connect
Confirm both endpoints exist and are paired; ComCon and legacy app use opposite endpoints. Check driver version/signature. ComCon does not bundle com0com or repair it.
Radio does not answer / wrong values
Recheck model, framing, serial settings, radio address and client settings against the actual device. Bridge start alone does not establish model support. See release notes for Yaesu and other model limits.
IPC handshake is rejected
Check IPC enabled/profile explicitly started, UUID mapping, version and competing client. Follow setup order and keep both pipes open.
Missing ACK, timeout or disconnect
Correlate session UUID and notification sequence. Do not replay the last CAT record. Establish a new session only after reviewing status/fault cause.
Legacy client unavailable after disconnect
Read legacy status/fault. Use Recover Legacy only when enabled and the cause is corrected. Recovery does not prove stream synchronization.
Configuration invalid/stale
Load the intended file, validate it and compare ports with Windows. Check the remembered configuration path if the file moved.
Help page is missing
Restore the release's Help folder from the verified package. There is no online fallback; do not use an unverified replacement.

12. Logs and diagnostics

Local diagnostic material is under %LOCALAPPDATA%\ComCon\. Structured development-fault entries are in Logging\ComCon-development-faults.jsonl (UTC, component, profile and bounded message). Raw CAT capture is Logging\ComCon-raw-cat.jsonl, with rotated files named ComConRawCatLog_*; each is limited to 1 MiB and up to ten files are retained. The raw-capture preference is Logging\ComCon-raw-cat-capture.json. UI colors are in UiColors.json; window-position data may be under Windows\.

Privacy: Raw CAT capture can contain station identifiers, commands, radio responses and sensitive activity. Enable it only if needed. Review/redact logs, call signs, serials, paths, UUIDs and configuration details before attaching anything to a public issue. Do not publish configuration files or captures by default.

Capture is off by default on a fresh install and can resume on later launches if enabled. Changing it does not start a bridge. Capture requires CI-V or Kenwood ASCII record framing; it is suspended for an active profile using unsupported framing. Logs/captures are diagnostic evidence only: they do not authorize retries or confirm radio state. Keep only relevant evidence and redact it yourself before sharing.

13. Backup, updates, rollback and uninstall

Before an update

  1. Stop active profiles and close ComCon normally.
  2. Back up the portable installation and every configuration file saved elsewhere. Keep the known-good ZIP and checksum for rollback.
  3. Download the new release and verify its SHA-256. Extract to a new user-writable folder first; do not overwrite your only working copy.
  4. Read release notes for schema/model/known-issue/migration changes. Load the intended configuration, validate ports, then start only after operator review.

Automatic configuration migration, rollback and session restoration are not promised. Preserve the previous package/configuration until the new version is reviewed. Per-user UI settings, positions, logs/captures and first-use dismissal are separate from the executable package and normally survive replacing its folder.

Uninstall

Stop every active bridge and close the app. Back up settings/logs/captures you need. Delete the extracted application folder and, if you also want to remove per-user ComCon data, delete %LOCALAPPDATA%\ComCon. This may include UI preferences, first-use state, positions, logs and captures. Configurations saved elsewhere are not automatically deleted; remove them only after confirming they are no longer needed. Uninstall any virtual COM driver separately using its supported instructions.

14. FAQ and known limitations

Do I need to install .NET?
No separate installation is needed for the planned self-contained ZIP. Source builds have different prerequisites.
Does ComCon transmit or tune automatically?
Starting alone does not initiate transmit/tune. RAW may forward client transmit/tune bytes, so it is not a safety filter.
Does IPC confirm radio commands?
No. WRITE_SUCCEEDED reports the physical write only. The client interprets replies; no delivery outcome certifies safety/completion.
Do I need com0com?
Only if a legacy COM client uses RAW and needs a virtual pair; not for IPC-only use.
Does ComCon start saved profiles automatically?
No automatic startup-session restoration is implemented; start/list actions require user review and confirmation.
Is every radio/firmware certified?
No. Initial intended scope is IC-7400, IC-7600 and TS-590SG, but support must be checked per release. Yaesu is experimental and has no command IPC.
Does an offline test prove radio safety?
No. Offline tests cannot certify a radio, driver, firmware or operating setup. Live checks need separate operator approval.

Release-specific open gates can include driver/signature compatibility, model/firmware acceptance, packaging or other items noted in that release. This guide is not evidence that a gate has passed.
